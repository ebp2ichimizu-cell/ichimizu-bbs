# Firestoreルール変更案

## 現在の確認状況

リポジトリには既存ルールがなく、Firebase ConsoleのCloud Firestore画面も確認しましたが「データベースの作成」が表示され、既存データベース・公開ルールは表示されませんでした。したがって現在公開中のルール全文は未取得・未確認です。`firestore.rules.proposed`は実装と対応する**変更案**であり、本番へ自動適用する設定は追加していません。実際にデータベースが未作成なら、作成時にリージョンを選び、変更案を検証した上で設定してください。

Firebase Console → Firestore Database → ルールで現在の全文を取得・保存してください。既存のコレクションに必要なアクセスを維持しながら、変更案の関数と`bbsCategories`・`bbsPosts`のmatchを統合します。既存のルール全文をそのまま変更案で置き換えないでください。

特に`match /{document=**}`等で`allow write: if true`、期限付きのテストモード、任意のログインユーザーの書き込みを許可していないか確認します。Firestoreは一致するallowのいずれかがtrueなら許可します。**掲示板内でdeleteをfalseにしても、別の広いmatchが許可すれば削除可能**です。広いallowが掲示板コレクションに重ならないよう、既存コレクションのmatchへ範囲を限定する必要があります。[Firebase公式の条件評価説明](https://firebase.google.com/docs/firestore/security/rules-conditions)。

## 変更案の権限

|対象|匿名閲覧|共通UIDの作成|共通UIDの更新・削除|
|---|---|---|---|
|bbsCategories|可|不可|不可|
|bbsPosts|可|可|不可|
|bbsPosts/{postId}/replies|親投稿が存在する場合のみ可|親投稿が存在する場合のみ可|不可|

共通UIDは`7kewpVCwEMeWkxmzXEK6BRUsxXl1`です。Authenticationのpasswordプロバイダーでログインした当該UIDだけを許可します。ニックネームを認証の代わりには使いません。UIDを変更する場合は`js/config.js`とルール案の両方を更新します。

許可するフィールドを限定し、文字列型・非空白・文字数・登録済みactiveカテゴリー・サーバー時刻を検証します。クライアントはUTF-16の長さで保守的に制限します。絵文字等は画面上の1文字が複数として数えられることがあります。

## 公開前のルール検証

Consoleのルールシミュレーター、またはFirestore Emulatorで以下を確認します。クライアント画面のテストだけではサーバーの許可・拒否を保証できません。

- 匿名：カテゴリー・投稿・返信は読める。書き込みは拒否。
- 別UID：投稿・返信は拒否。
- 共通UID（passwordプロバイダー）：正しいフィールドとserverTimestampを持つ投稿・返信は許可。
- 共通UID：30／100／5000／2000文字の各上限は許可、超過・空白のみ・数値型・余分なフィールド・欠落フィールド・偽造時刻は拒否。
- 共通UID：存在しない／無効カテゴリー、存在しない親投稿への返信は拒否。
- 共通UID：投稿・返信のupdateとdelete、カテゴリーのcreate/update/deleteは全て拒否。
- 既存サイトが同じFirebaseを使用している場合は、既存コレクションの必要なアクセスを維持していることを確認。

現在のルールと比較・統合し、上記検証が通るまでは公開ルールを変更しないでください。

## 管理者削除（別途設計・未実装）

共通アカウントには削除権限を付与しません。当面の削除は管理者がFirebase Consoleで行います。親投稿を削除する場合は返信サブコレクションも対象にしてください。

管理者画面を追加する場合は、共通アカウントとは別の個別管理者アカウントを使い、管理者ロールを信頼できるサーバーから設定します。削除は認証・管理者ロールを検証するバックエンドでAdmin SDKを使用し、対象確認と監査ログを残します。親投稿と返信の再帰削除にはサーバー側での権限検証が必要です。今回のルール案には管理者delete許可やクライアント削除APIは追加していません。

共通アカウントでは利用者をUIDで個別識別できません。ニックネームは任意であり本人確認や管理権限の根拠にできません。
